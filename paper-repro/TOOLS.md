# paper-repro tools

Every tool returns its output as JSON text, except where noted as plain text.

| Tool | Description of input arguments | Description of output arguments | Tool description |
|---|---|---|---|
| Docker_build(dockerfile) | `dockerfile`: path to the Dockerfile, relative to the paper's folder. Optional: `tag`, the image name (defaults to the spec's image, e.g. `repro-uap:latest`); `context`, the build folder (defaults to the spec's context). | `status`: OK, FAILED or ERROR; `image`: tag of the built image; `seconds`: build time; `log`: path to the full build log; `log_tail`: last 4,000 characters of the log, on failure | Build docker image |
| Reproduce_metric(metric, container) | `metric`: name of a metric in the paper's spec (e.g. `victim_accuracy`); `container`: an image tag to start a fresh GPU container from, or the name of an already-running container (defaults to the spec's image) | `status`: OK, RUN_FAILED, NOT_FOUND or ERROR; `value`: the extracted number; `matched_line`: the output line it came from; `reused_previous_run`: true if an earlier identical run was reused; `log`: path to the run log; `log_tail`: end of the log, on failure | Use container to run and obtain metric value |
| Validate_metric(metric) | `metric`: name of a metric that has already been reproduced | `status`: PASS, FAIL or NO_RECORD; `reproduced` and `recorded` values; `difference`; `allowed_difference`; `tolerance` (absolute or relative); `source`: where the recorded value came from (e.g. "Table 1") | Compare reproduced metric with record value |
| Find_run_commands(repo_path, dockerfile) | `repo_path`: cloned repo folder; `dockerfile` (optional): the paper's Dockerfile from Team 1 | `documented_commands` (from README/scripts, with file:line), `entry_scripts`, `script_options` (via Team 3's `list_arguments` scanner when available), `container`: base image, working folder, where the code is placed, commit | Report how a repo can be run, as the basis for choosing the spec's command |
| Generate_spec(paper_name, dockerfile, repo_path, command, metrics, data_dir, data_mount, record_path, gpu, timeout_minutes, tolerance) | The Dockerfile (Team 1), the cloned repo, the chosen run command, metric names (comma-separated, as in Team 2's record); optional: host data folder, its container path (otherwise worked out), Team 2's metrics record, GPU, time limit, tolerance | `status`; `spec_path`; the `spec` text; `how_it_was_decided` (working folder, data mount, env, each with evidence); `warnings`; `how_results_are_printed` (print statements, flagged when inside a loop) | Write the paper's spec.yaml: working folder from the Dockerfile, data mount from data paths in the command and hard-coded in the code, env and GPU needs, paper values from the record. Metric patterns start as placeholders, set after the first run |
| Load_paper_spec(spec_path) | `spec_path`: path to a paper's `spec.yaml` | `paper` name, `repo`, `image`, `dockerfile`, `run_command`, `gpu`, `volumes` (data folders), `notes`, and each metric's `recorded` value, `tolerance`, `source` and `command` | Load a paper's reproduction spec and make it the active paper; must be called before the three tools above |
| Update_spec_metric(metric, recorded, source, tolerance, pattern, after, occurrence) | `metric`: metric name; then only the fields to change: `recorded` (paper's value), `source` (table/row/column), `tolerance`, and for reading the run output `pattern`, `after` (regexes) and `occurrence` (which match to use: first, last, or an index such as -1) | `status`: OK, PARTIAL (paper fields saved, output-reading change refused) or ERROR; the fields saved; for an accepted output-reading change, `value_from_latest_run` and `matched_line`: the number it now reads and the output line it came from | Edit one metric in the spec, changing only the given fields; output-reading changes are accepted only if they find a number in a real run log, and the reproduced value is updated to match |
| Read_paper(source, search, start_line, num_lines) | `source`: paper PDF URL or local path; optional `search` (regex), `start_line` and `num_lines` (default 60) | Plain text: with no options, an outline of table/figure captions and section headings with line numbers; with `start_line`, those lines of the paper; with `search`, matching lines with surrounding context | Read a paper PDF as numbered text to find the values the paper reports |
| Inspect_repo(repo_url) | `repo_url`: git URL of the paper's code | `path`: where it was cloned; `files`: file list (up to 3 folders deep); contents of the README and dependency files (`requirements.txt`, `setup.py`, etc.) | Clone a repository and summarize it, as a basis for writing a Dockerfile and spec |
| Read_file(path, start_line, max_lines) | `path`: text file to read; optional `start_line` (default 1) and `max_lines` (default 300) | Plain text: the requested lines, numbered | Read part of a source file, e.g. to find a script's options or how it prints metrics |
| Write_file(path, content) | `path`: file to write (only allowed inside the workspace or papers folders); `content`: full file text | Plain text: confirmation with the number of characters written, or ERROR (path outside the allowed folders, or a spec that wouldn't load) | Write a new Dockerfile or spec for a paper; refuses to save a spec that is invalid |

Reproduced values are also written to `reproduced_record.json` in Team 2's record format. The supporting tools exist so the LangChain agent can set up a new paper on its own: read the repo and paper, write the Dockerfile and spec, then run the three core tools.
